Part 1: Foundations

What is Database Security? (The CIA Triad Explained)

Why database security is about protecting data from being seen, changed, or destroyed.

1. Confidentiality

💡 Only authorized eyes can see the data.
  • Protects confidential identity data like student NRC numbers and emails.
  • Prevents data leaks to unauthorized students or external hackers.
  • Enforced via user permissions and masked views (vw_student_grades).

2. Integrity

💡 Data cannot be secretly altered or faked.
  • Ensures exam marks and academic standings remain 100% genuine.
  • Stops rogue actors from tampering with grades or student records.
  • Enforced using triggers, constraints, and audit logging.

3. Availability

💡 The database is up when you need it.
  • Ensures lecturers and students have timely, reliable access during exams.
  • Guards against accidental deletion of tables or Denial-of-Service crashes.
  • Enforced using backups, clustering, and privilege limits.
Speaker Notes (Comfort Penyengwe): "To understand database security, we look at the CIA Triad: Confidentiality, Integrity, and Availability. Confidentiality means student NRCs stay private. Integrity means nobody can secretly change their grade from 50 to 90. Availability means the database is always online. Real security isn't just one firewall; it has to be built inside the database engine itself."

Part 1: Threat Landscape

How Databases Get Hacked (Common Threats)

The two biggest dangers in database systems: SQL Injection and Privilege Abuse.

1. SQL Injection (The #1 Web Attack)

💡 Tricking the database into running the hacker's code.
  • Occurs when an application glues user text directly into an SQL query string.
  • Attacker types into an NRC search box: ' OR '1'='1
  • The database evaluates '1'='1' as TRUE for every single row.
  • Result: Critical data breach! The entire student registry, NRCs, and emails are dumped onto the screen.

2. Privilege Abuse & Insider Threats

💡 Giving regular users too much database power.
  • If a regular account has DROP or DELETE rights, one rogue action destroys the entire database.
  • Missing Audit Trail: If someone alters a grade, but there is no audit log, nobody knows who did it.
  • Weak Authentication: Default root passwords or passwords stored in plaintext.
Speaker Notes (Comfort Penyengwe): "The most famous database attack is SQL Injection. When application code takes user input and concatenates it directly into an SQL query, an attacker can input quotes and SQL keywords to trick the database into dumping all records. The second danger is giving regular users too much power—if a student can run an UPDATE command on the grades table, the integrity of the university is broken. Now, Gideon Namuya will explain how we defend against these threats."

Part 2: Defensive Controls

Role-Based Access Control & The Principle of Least Privilege

Users should only be allowed to do what their specific job requires—nothing more.

Administrator (DBA)

💡 Full system control for maintenance.
  • Account: sec_admin
  • Permissions: GRANT ALL PRIVILEGES
  • Can create tables, manage backups, and configure user accounts.
  • Restricted strictly to authorized IT staff.

Lecturer (Academic Staff)

💡 Can grade students, but cannot destroy data.
  • Account: sec_lecturer
  • Permissions: SELECT, INSERT, UPDATE on grades.
  • CANNOT drop tables (DROP denied).
  • CANNOT delete student accounts (DELETE denied).

Student (Undergraduate)

💡 Strict read-only access to their own grades.
  • Account: sec_student
  • Permissions: SELECT on masked view only.
  • CANNOT view peer NRC numbers.
  • CANNOT update or alter any mark (Error 1142 Access Denied).
Speaker Notes (Gideon Namuya): "Thank you, Comfort. To defend against privilege abuse, we use Role-Based Access Control under the Principle of Least Privilege. In simple terms: an Admin can do everything; a Lecturer can only enter and update marks; and a Student has strict read-only access to view their own grades. Even if a student tries to hack the system and run an UPDATE command, the database engine blocks it immediately with an Access Denied error."

Part 2: Defensive Controls

How Parameterized Queries Stop SQL Injection Completely

The golden rule: Treat user input strictly as plain data, never as executable SQL instructions.

Vulnerable: Dynamic String Concatenation

💡 The database gets tricked into running user text as commands.
  • SELECT * FROM students WHERE nrc = 'INPUT'
  • User types: ' OR '1'='1
  • What runs: WHERE nrc = '' OR '1'='1'
  • Why it breaks: Quotes close the string; OR '1'='1' becomes live SQL logic!
  • Result: Every confidential student record and NRC is leaked.

Secure: Parameterized Prepared Statement

💡 Database compiles query FIRST, before input arrives.
  • cursor.execute("SELECT * FROM students WHERE nrc = ?", (input,))
  • User types: ' OR '1'='1
  • What runs: Searches literally for a student whose exact NRC text contains quotes and OR.
  • Why it works: Placeholder ? treats input purely as a data literal.
  • Result: 0 records matched. Attack completely neutralized!
Speaker Notes (Gideon Namuya): "Now look at why Parameterized Queries are the ultimate defense against SQL Injection. In vulnerable code, strings are glued together, so the attacker's quotes become SQL commands. But in a Parameterized Query—or Prepared Statement—the database engine pre-compiles the query template first. When the attack payload arrives, the database treats it purely as plain text. It searches for an NRC containing quotes, finds nothing, and the attack fails completely."

Part 2: Defensive Controls

Data Encryption & Tamper-Evident Audit Logging

Protecting data on disk with encryption, and using database triggers to catch mark tampering.

1. Cryptographic Protection (Hashing & Encryption)

💡 If the database is stolen, the data cannot be read.
  • Password Hashing: Passwords stored using SHA-256 with salt. Even DBAs cannot reverse them.
  • Data in Transit: TLS/SSL network encryption prevents eavesdropping.
  • Data at Rest: Sensitive identity columns like NRC numbers can be encrypted so raw files on hard drives are protected.

2. Automated Database Triggers (Audit Trail)

💡 A security camera recording every change in the database.
  • What if an authorized lecturer alters a student's grade from 40 to 85?
  • We built an automatic trigger: trg_grades_audit_update.
  • Every time an UPDATE occurs, the trigger silently records: who did it, the exact timestamp, the old mark, and the new mark.
  • Guarantees Non-Repudiation: Nobody can deny their actions.
Speaker Notes (Gideon Namuya): "Our third layer of defense is Encryption and Auditing. Passwords are saved as one-way salted hashes so they cannot be stolen, and connections are encrypted. Furthermore, to prevent internal fraud, we created an automatic database trigger on the grades table. If a grade is modified, the database silently records who changed it, the previous score, and the new score. Now, Lubuto Matambo will explain the industry tools and our prototype architecture."

Part 3: Industry & Design

Enterprise Database Security Systems & Tools

How major enterprise environments implement these security controls at scale.

MySQL Enterprise

💡 Commercial security suite.
  • Enterprise Firewall: Inspects incoming SQL traffic and blocks injection attempts.
  • Transparent Data Encryption (TDE): Encrypts table data on hard drives automatically.
  • Enterprise Audit: Tamper-resistant compliance logging.

PostgreSQL Security

💡 Advanced open-source controls.
  • Row-Level Security (RLS): Automatically filters rows based on the logged-in user session.
  • pg_audit: Detailed logging of all administrative actions.
  • SCRAM-SHA-256: Modern authentication.

Vault & DAM Systems

💡 Password rotation & monitoring.
  • HashiCorp Vault: Generates temporary database passwords that expire automatically (no hardcoded passwords).
  • IBM Guardium / Imperva: Continuous traffic monitoring and anomaly alerts.
Speaker Notes (Lubuto Matambo): "Thank you, Gideon. In large corporations, database security is powered by enterprise tools. MySQL Enterprise provides an automated Firewall that stops SQL injection, and Transparent Data Encryption to protect disks. PostgreSQL has Row-Level Security so users only see their own rows. And tools like HashiCorp Vault automatically rotate passwords so developers never have to write hardcoded credentials in code."

Part 3: Industry & Design

Benefits, Real-World Trade-offs & The Zambia Data Protection Act

Balancing security with speed, and meeting Zambian legal requirements.

Key Benefits & Legal Compliance

💡 Keeping the university reputable and compliant with law.
  • Preserves Academic Standing: Prevents unauthorized grade inflation or bribery.
  • The Zambia Data Protection Act No. 3 of 2021: Legally requires universities handling personal records (such as NRC numbers) to enforce technical security.
  • Damage Containment: Even if a student account is compromised, RBAC prevents privilege escalation.

Real-World Challenges & Costs

💡 Security always has costs you have to manage.
  • Performance Overhead: Running audit triggers on every update and encrypting columns consumes CPU and disk resources.
  • Privilege Management: Maintaining user roles across an expanding organization requires continuous administrative effort.
  • The Human Factor: Technology cannot stop people from writing passwords on sticky notes or falling for phishing.
Speaker Notes (Lubuto Matambo): "Database security provides indispensable protection. In Zambia, under the Data Protection Act of 2021, universities processing personal data like NRC numbers are legally required to enforce technical safeguards. But security also brings trade-offs: encrypting columns and firing audit triggers uses server CPU, and maintaining user permissions requires continuous administration. Furthermore, technology cannot fix human mistakes like sharing passwords."
